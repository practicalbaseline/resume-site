Token Management: Best Practices for LLM Applications

8 min read

Every call to a large language model costs tokens. Every token costs money and time. If you treat the context window as infinite, you'll pay for it — in latency, in bills, and in degraded output quality when the model loses focus in a bloated prompt.

Token management isn't an optimization you add later. It's a design constraint you build around from the start, the way you'd design around memory limits or network bandwidth.

What is a token?

A token is the atomic unit a language model reads and generates. It's not quite a word — common words like "the" are usually one token, but longer or unusual words get split into subword pieces. Rough rule of thumb: 1 token ≈ 4 characters in English, or about 750 words per 1,000 tokens.

Both your input (prompt) and the model's output (completion) consume tokens. Most providers charge separately for input and output tokens, with output typically costing more.

Know your context window

Every model has a maximum context window — the total tokens it can process in a single request (input + output combined). Common ranges today:

  • 8K–32K tokens — older and smaller models
  • 128K tokens — current mainstream (GPT-4o, Claude 3.5)
  • 200K–1M+ tokens — extended-context models

A larger window doesn't mean you should fill it. Models often perform worse on tasks buried in the middle of very long contexts — a phenomenon researchers call the "lost in the middle" problem. Use the window you need, not the window you have.

Best practices

1. Measure before you optimize

Use your provider's tokenizer (or a library like tiktoken) to count tokens before sending requests. Log token usage per request, per user, and per feature. You can't manage what you don't measure. 

import tiktoken

enc = tiktoken.encoding_for_model("gpt-4o")
tokens = enc.encode("Your prompt text here")
print(f"Token count: {len(tokens)}")

2. Structure your prompts deliberately

Put the most important instructions at the beginning and end of your prompt — models weight these positions more heavily. Use clear section headers, keep system prompts stable and cacheable, and avoid repeating context the model already has.

  • System prompt — stable instructions, persona, constraints
  • Context — retrieved documents, conversation history
  • User message — the actual query

3. Summarize and compress history

In multi-turn conversations, raw message history grows linearly. Instead of sending every prior message, summarize older turns into a compact state object. Keep recent messages verbatim for coherence; compress everything older. 

# Instead of sending 50 messages:
messages = [
  {"role": "system", "content": system_prompt},
  {"role": "user", "content": conversation_summary},  # compressed
  {"role": "assistant", "content": "Understood."},
  {"role": "user", "content": last_3_messages},       # recent verbatim
  {"role": "user", "content": current_query},
]

4. Retrieve, don't dump

For RAG (Retrieval-Augmented Generation) systems, retrieve only the chunks relevant to the query — don't stuff your entire knowledge base into the prompt. Use semantic search, rerank results, and set a hard token budget for retrieved context.

5. Set output limits

Use max_tokens (or equivalent) to cap completion length. A runaway generation can double your costs on a single request. Match the limit to the task: a classification label needs 10 tokens; a code review might need 2,000.

6. Cache what repeats

Many providers now offer prompt caching — if the beginning of your prompt is identical across requests, those tokens are served from cache at reduced cost. Structure prompts so static content (system instructions, reference docs) comes first and varies last.

7. Choose the right model for the task

Not every task needs your most capable (and expensive) model. Route simple queries to smaller models, reserve large models for complex reasoning. A good classifier or router can cut token costs by 60–80% without sacrificing quality on hard tasks.

Cost estimation framework

Before shipping a feature, estimate its token economics:

  1. Count average input tokens per request
  2. Estimate average output tokens per request
  3. Multiply by your model's per-token price
  4. Multiply by expected daily requests
  5. Add 30% buffer for retries, errors, and growth

If the monthly number makes you uncomfortable, redesign before you deploy.

Red flags to watch for

  • Prompts that grow unboundedly with conversation length
  • Dumping full documents when a summary would suffice
  • No max_tokens limit on completions
  • Using a frontier model for tasks a smaller model handles fine
  • No logging or alerting on per-user token consumption
  • Retrying failed requests without truncating the prompt

Token management is the memory management of the LLM era. The builders who treat it as a first-class engineering concern — not an afterthought — will ship faster, spend less, and build systems that actually scale.
